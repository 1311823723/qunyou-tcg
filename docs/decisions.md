原因：上一轮虽然强化了敌我辨识，却隐藏了用户已有资产并产生大块留白，未满足实际体验要求。维护入口：[界面风格](style-guide.md)、[产品规格](auto-battle-product.md)。

## DEC-006：流派名优先表达核心操作

2026-09-08：预组组名继续承担称号和世界观功能，流派名则优先让玩家一眼看出主要操作。南山五采用「破魔组／反制流」，KGY采用「巡界组／骑士流」；前者突出等待技能后反击，后者直接提示六种骑士卡。技术 ID 不随名称变化。

影响：预组页面和攻略必须同时展示组名、流派关键词和一句玩法说明；流派目录中的 `name` 继续作为正式玩家可见名称，技术 ID 不随命名讨论变化。

交叉组沿用「交叉组／交叉流」，因为其核心不是单一定位，而是有意识地交替使用角色技能与【出刀】。

## DEC-007：再战以双方同意为边界

2026-09-09：采用原房间内发起／回应邀请。沿用预组与回到准备室换组分别明确确认，任何一方不能单方面覆盖已结束的牌桌；断线取消邀请，过期请求不可执行。接受后重建对局状态，保留房间座位、观战与命令去重，不在旧状态上逐项重置技能字段，减少跨局残留。继续复用正式开局洗牌和规则引擎。

首轮结果只展示已有公开胜负、回合及体力，不推断伤害统计或隐藏信息。历史日志在新局清空，持久战报留待独立需求。影响：[产品规格](auto-battle-product.md)、[Beta 说明](auto-battle-beta.md)。

## DEC-008：钛晶化由本体声明，PET 每局只选一次

2026-09-10：后续四张本体采用各自专属的钛晶化形态。只有卡面和正式数据明确写有钛晶化的本体才拥有该形态；玩家满足该本体自己的条件后翻到该本体背面，并选择六种通用 PET 属性中的一种覆盖。PET 每局只能选择一次，不能更换或移除。

钛晶化不是公共主动技能，也不改变角色牌的主定位。本体正面与背面优先使用自动触发、保守的被动特性；每张本体最多一个简短主动效果，避免本体盖过角色牌成为预组的操作核心。六种 PET 只提供单一方向的轻量被动修正，具体数值必须经过四张本体交叉试配后再确认。

与 Mega、Z 招式和极巨化一样，钛晶化是否存在由本体卡决定。除非某张本体明确允许，同一局不叠加另一种额外形态。详细设计边界见[钛晶化本体设计草案](tera-type-design.md)。

影响：计划将角色池从 120 张扩展到 160 张时，四张新本体各自优先新增约 10 张核心／桥接角色，其余预组位置继续复用已有角色；在本体和 PET 设计定稿前不新增正式卡牌数据或自动化模块。

## 小程序样式与文本的硬约束，以及验证门禁：2026-09-21

第四轮在真实微信开发者工具里跑通后，把三条平台约束固化为可执行的检查，而不是只写在文档里：

1. **WXSS 禁用通配选择器。** 实测 `*`、`.a *`、`.a > *`、`*.b` 全部让工具自带的 `wcsc` 报 `unexpected token '*'`，且是**整个文件**编译失败（不是跳过该条规则），表现为全站白屏。「减少动态效果」改用逐个类名列出，新增带动画的类必须同步加入。
2. **禁止 `<text user-select wx:for>`。** 两者同处一棵子树时 `<text>` 被提升为块级，行内流被破坏：项目符号独占一行、加粗与正文混排的段落被拆成多行。正文块 205 个中 101 个受影响，故移除 `user-select`（项目无「可选中／长按复制」要求）。
3. **WXML 文本不解码 HTML 实体，**`&amp;` 会原样显示，直接写 `&`。

验证门禁改为**优先调用工具自带的真实编译器**：`wcc`（WXML）与 `wcsc`（WXSS）随开发者工具安装在本机，`npm run mini:test` 第 21 项逐个文件真编译；未安装工具的环境打印 `[skip]` 而不是失败，避免 CI 误报。两条纯静态兜底（禁用 `*`、禁用 `user-select + wx:for`）在任何环境都执行。三条防线均以人为注入反向验证过能准确报出文件与行号。

理由：此前把「本地静态校验」与「微信编译器」当作两回事，导致 `*` 这种必然失败的写法通过了全部 19 项测试却让小程序全白。只要能拿到真编译器，就不应再用近似手段代替。详见[验收记录](miniprogram-verification.md)。


## 小程序信息架构：首页做启动台，卡牌列表独立成栈页：2026-09-21（部分已被 2026-09-22 取代）

> **2026-09-22 更正：** 第 1、3 条已失效——首页不再是启动台，改为收藏室场景并恢复展示本体与预组；图鉴 tab 直接是卡册，不再经分类入口；骑士卡改为独立牌种，「手牌」只含基础牌与行动牌。第 2、4、5 条与末尾的平台约束仍然有效。取代后的完整形态见[产品规格](miniprogram-product.md)与下方「2026-09-22 小程序信息架构」。

用户反馈首页应当是「规则／卡牌／预组」三个入口、原首页内容归到预组页、卡牌页像网页版一样分本体／角色／手牌。据此确认：

1. **首页只承担导航与品牌，不再承载预组内容。** 预组主视觉、新手入口、全部预组网格移到 `pages/decks`。首页保留全量搜索与收藏／最近浏览两个回访入口。
2. **卡牌 tab 只能做入口，分类列表必须是栈页。** 微信 tabBar 页面之间只能用 `switchTab`，`navigateTo` 会报 `can not navigate to a tabBar page`；因此新增 `pages/collection`。这不是风格选择，是平台约束决定的落地方式。
3. **手牌分类含骑士卡。** 骑士卡（6 种）与基础牌、行动牌同属牌堆资源，且没有正式成卡图。把它们并入「手牌」并在入口描述里写明「含骑士流骑士卡」，比新增第四个入口更贴合用户表述，也不会让骑士卡失去入口。
4. **分类数量由数据计算，不手写。** portal 上的 12／120／20／3／12 全部来自 `catalog`，新增卡牌不需要改页面。
5. **点击容器用 `<view role="button" hover-class>` 而非 `<button>`。** 微信 `button` 自带内边距、`min-height`、`::after` 边框与 `text-align:center`，做卡形容器时样式互相干扰（完整规则页的章节目录也有同样的观感问题）。需要整块可点的卡片统一走 view。

**平台约束补充：`navigateTo` 的中文查询参数不自动解码。** `?kind=本体` 到达页面时 `options.kind` 是 `%E6%9C%AC%E4%BD%93`，必须在 `onLoad` 自行解码，否则会静默落到默认分支。此类缺陷 Node 侧测试无法覆盖（Node 传的是原始字符串），只能靠工具内驱动发现，故保留该验证通道。详见[产品规格](miniprogram-product.md)、[架构](miniprogram-architecture.md)与[验收记录](miniprogram-verification.md)。

## 2026-09-22 小程序信息架构：场景式首页 + 图鉴 tab 即卡册

用户在此基础上自己改定了最终形态，据此确认（取代 09-21 同名条目中的第 1、3 条）：

1. **首页回到「展示内容」而不是「只做导航」。** 采用暖灯／木棕／酒红的收藏室场景，中部是本体精选卡架（两侧卡背 + 中间正式完整成卡图，点击进入详情），下方是图鉴／入门入口、精选预组横向卡册与按需出现的收藏／最近浏览。文案与数量全部来自 `catalog`／`presentation`，页面不写死卡牌文字。
2. **图鉴 tab 本身就是可搜索的卡面网格，不再只是一层分类入口。** 减少一次跳转；搜索与牌种切换常驻，定位与预组筛选折叠进「筛选 ＋」，避免首屏被筛选项占满。
3. **`collection` 降级为旧深链兼容页**，与 `cards` 共用同一套 `GROUPS`/`SUBS`/筛选逻辑。代价是两处筛选口径必须同步维护，因此把「同步回归」写进 `mini:test` 与[架构](miniprogram-architecture.md)。
4. **骑士卡独立成牌种。** 它不属于任何一方手牌，与基础牌／行动牌并列；「手牌」只含基础牌与行动牌（4 + 10）。口径：本体 12 ／ 角色 120 ／ 基础牌 4 ／ 行动牌 10 ／ 骑士卡 6，合计 152。
5. **长文改两级阅读。** 正式规则 34 章改为「目录 → 单章」，单卡改为视觉列 + 阅读列（卡牌事实／完整效果），都是为了让手机上的长文可读，而不是为了增加层级。
6. **底栏文案定为 首页／图鉴／预组／指南。**

理由：09-21 的「启动台 + 三分类入口」解决了「不知道从哪进」，但多出两次跳转，且首页失去观赏性——用户明确更在意看到真正的卡。直接给卡册、把筛选折叠，是「少一层菜单」与「首屏不被筛选项淹没」之间的折中。详见[产品规格](miniprogram-product.md)、[架构](miniprogram-architecture.md)、[验收记录](miniprogram-verification.md)第七轮。
